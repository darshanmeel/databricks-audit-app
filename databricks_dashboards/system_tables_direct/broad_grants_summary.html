Broad grants, in brief

A two-minute read. Every query, step and column: the detailed guide.

What it is for

Lists every privilege granted in Unity Catalog, with who granted it and when, and flags the broad ones: ALL PRIVILEGES on a catalog, schema or table, and anything granted to account users.

How the tables join

Grey: system tables. Blue border: a shared check (its steps are listed under Steps). White: steps of the query. Green: the rows the dashboard shows. ◆ marks the columns the joins use.

  1. access.audit → ev: updatePermissions, status 200
  2. ev → granted: explode changes, then add
  3. granted → dashboard rows: flag broad
  4. access.workspaces_latest → dashboard rows: JOIN ON workspace_id

  1. access.audit → ev: unityCatalog updatePermissions, 200, window; one per event_id
  2. ev → per_grantee: from_json(changes); explode
  3. per_grantee → granted: explode(c.add); ALL PRIVILEGES = ALL_PRIVILEGES
  4. granted → judged: ALL_PRIVILEGES on catalog/schema/table; account users
  5. judged → dashboard rows: actor type from the actor
  6. ws → dashboard rows: LEFT JOIN ON workspace_id

The system tables

System tableWhat it holds
system.access.auditOne row per action in the account: who, when, which workspace, the service and action, the request and its response. Kept for 365 days.
system.access.workspaces_latestEach workspace's id and name.

How it works

  • Every GRANT, from SQL, the UI or the API, writes an updatePermissions row to system.access.audit with the object, the grantee and the privileges.
  • The dashboard splits it into one row per privilege and flags the broad ones.
  • It shows who granted it, a person or a service principal, and when.

Example: a grant becomes an audit row

The query, simplified

The core of it; runs as is in a SQL editor. The dashboard's full queries, step by step: the detailed guide.

-- Every privilege granted, one row each; broad ones flagged.
SELECT a.event_time, a.user_identity.email AS granted_by,
       a.request_params['securable_full_name'] AS object,
       g.principal AS grantee, p AS privilege,
       p = 'ALL_PRIVILEGES' OR lower(g.principal) = 'account users' AS critical
FROM system.access.audit a
LATERAL VIEW explode(from_json(a.request_params['changes'],
                               'ARRAY<STRUCT<principal: STRING, add: ARRAY<STRING>>>')) x AS g
LATERAL VIEW explode(g.add) y AS p
WHERE a.service_name = 'unityCatalog' AND a.action_name = 'updatePermissions'
  AND a.response.status_code = 200
  AND a.event_date >= current_date() - 30
ORDER BY critical DESC, a.event_time DESC;

The rules

TermMeans
CriticalALL_PRIVILEGES on a CATALOG, SCHEMA or TABLE, or any privilege to account users.
Actor typeService principal when the actor is a UUID (application id), User when it is an email, else Other (system).

Good to know

  • Only grants still in the audit log (365 days).
  • Revokes are left out; Admin changes shows them.
  • The object and grantee come from the event's request_params (securable_type, securable_full_name, changes); if Databricks changes that layout the table goes empty. The detailed guide has a query to check it.
