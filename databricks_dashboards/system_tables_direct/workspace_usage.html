What this dashboard is for

Shows how many people log in per workspace class and per workspace in a month, and which workspaces have had no activity for 90 days or more, as candidates to retire.

How the tables join

Grey: system tables. Blue border: a shared check (its steps are listed under Steps). White: steps of the query. Green: the rows the dashboard shows. ◆ marks the columns the joins use.

  1. access.audit → logins: logins, status 200, emails
  2. access.audit → seen: MAX(event_date)
  3. logins → active users: COUNT(DISTINCT user)
  4. access.workspaces_latest → active users: JOIN ON workspace_id
  5. seen → inactive workspaces: 90+ days or none
  6. access.workspaces_latest → inactive workspaces: LEFT JOIN: all workspaces

Databricks basics

TermWhat it means
WorkspaceOne Databricks environment (its own URL, users, jobs, clusters). An account holds many workspaces; the dashboards read all of them at once.
System tablesRead-only tables Databricks fills for the whole account under the catalog system (system.billing, system.lakeflow, system.compute, system.access). The dashboards read them live; there are no tables of our own.
Audit logsystem.access.audit: one row per action someone took (log in, grant, change a group, ...), with who did it, when, in which workspace, the request and whether it succeeded. Databricks keeps it for 365 days.
User, group, service principalA user is a person (an email). A group bundles users. A service principal is a non-human identity for automation (CI/CD, Terraform); in the audit log it appears as its application id, a UUID like 1b2c3d4e-....
Query, CTEA query is SQL. Each one here is a chain of named steps written WITH name AS (...), called CTEs; each step reads the ones before it, and one last SELECT gives the rows.

Rules and thresholds

RuleDefinitionWhy
Active userA person (an email) with at least one successful login (accounts service, a login action, status 200) in the picked month.People, not logins; service principals left out.
MonthAny day in the month picks the whole month; default this month.Monthly active users is a month figure.
ClassThe first LIKE pattern the lower-case workspace name matches; else Not classified.Set with --workspace-class when the dashboard is built.
InactiveNo audit event for 90+ days, or none in the last 365 days.Any event counts, scheduled jobs too: a workspace that only runs jobs is in use.

What it can miss

  • Some system tables only hold workspaces in the same cloud region as the metastore; if a workspace is missing, check its region.
  • The audit log keeps 365 days, so last activity can't be older than that.
  • Account-console logins (workspace 0) are left out: they are not a workspace.
  • Reading a year of audit log for last activity is the slowest part.

How to read a query

  • No snapshot. Each query reads the Databricks system tables directly, every time the dashboard opens or a filter changes.
  • Widgets share queries. Each widget reads one query and adds up its rows its own way (the Widgets table says how); widgets that read the same query always agree.
  • Each query reads like a recipe: named steps (WITH step AS (...), called CTEs), each building on the one before, then one final SELECT. A step named after a check (for example lakeflow_job_reliability) is a shared, tested check reused unchanged except for the dates; its own steps are listed under it.
  • Time Window: :time_range.min and :time_range.max are the dates picked in the Time Window filter (on Global Filters, or on the page). The end day counts in full.
  • Workspace and the other field filters need no SQL: Databricks keeps the rows whose column matches the pick.
  • $ is list price (usage x the SKU's list price), not the invoice.
  • Comments in the SQL (green, starting --) are added on this page only.

The queries

Monthly active users: who logged in, per workspace

Shows: Each person with at least one successful login to a workspace in the picked month. Used by: The active-user tiles and charts on Workspace usage.

Why it is built this way: A login in the audit log is the clearest sign someone used a workspace. Counting distinct people (not logins) shows reach; service principals are left out because they are automation, not users.

How its tables join

Grey: system tables. Blue border: a shared check (its steps are listed under Steps). White: steps of the query. Green: the rows the dashboard shows. ◆ marks the columns the joins use.

  1. ws → ws_class: every workspace
  2. classes → ws_class: LEFT JOIN ON lower(name) LIKE pattern; first match
  3. access.audit → logins: accounts, login, status 200, the month; DISTINCT
  4. logins → dashboard rows: people only (an email)
  5. ws_class → dashboard rows: LEFT JOIN ON workspace_id

1. System tables it reads

  • system.access.audit
  • system.access.workspaces_latest

2. Steps (CTEs), in order

  1. ws: Workspace id to name.
    Its SQL (6 lines)
    -- Monthly active users: who logged in, per workspace. Dates from the Month filter.
-- Workspace id to name.
ws AS (
  SELECT CAST(workspace_id AS STRING) AS workspace_id, workspace_name
  FROM system.access.workspaces_latest
)
  2. classes: The workspace classes: a LIKE pattern on the workspace name per class; none set means Not classified.
    Its SQL (6 lines)
    -- The workspace classes: a LIKE pattern on the workspace name per class; none set means Not classified.
classes AS (
  -- no classes set: every workspace reads Not classified
  SELECT CAST(NULL AS STRING) AS workspace_class, CAST(NULL AS STRING) AS name_pattern, 0 AS priority
  WHERE FALSE
)
  3. ws_class: Each workspace's class: the first pattern its name matches, else Not classified.

    What it brings, on the example:

    workspace_idworkspace_nameworkspace_class
    101analytics-prodNot classified
    Its SQL (7 lines)
    -- Each workspace's class: the first pattern its name matches, else Not classified.
ws_class AS (
  SELECT w.workspace_id, w.workspace_name,
         COALESCE(MIN_BY(c.workspace_class, c.priority), 'Not classified') AS workspace_class
  FROM ws w LEFT JOIN classes c ON lower(w.workspace_name) LIKE c.name_pattern
  GROUP BY w.workspace_id, w.workspace_name
)
  4. logins: Successful logins (accounts service, login actions, status 200) in the picked month, per workspace and person; account-console logins left out.

    What it brings, on the example:

    workspace_iduser_name
    101alice@example.com
    1017f3c2a10-5b4e-4d2a-9c11-2e8f6a0b4d93
    Its SQL (11 lines)
    -- Successful logins (accounts service, login actions, status 200) in the picked month, per workspace and person; account-console logins left out.
logins AS (
  SELECT DISTINCT CAST(workspace_id AS STRING) AS workspace_id,
         lower(COALESCE(user_identity.email, user_identity.subject_name)) AS user_name
  FROM system.access.audit
  WHERE service_name = 'accounts' AND action_name RLIKE '(?i)login'
    AND response.status_code = 200
    AND event_date >= CAST(date_trunc('MONTH', :month) AS DATE)
    AND event_date < add_months(CAST(date_trunc('MONTH', :month) AS DATE), 1)
    AND workspace_id IS NOT NULL AND workspace_id <> 0
)

3. Final query

One row per workspace and person; the widgets count distinct people.

4. Columns it returns

ColumnMeaning
workspaceThe workspace's name (its id when the name is unknown).
workspace_classThe workspace's class from its name pattern, or Not classified.
user_nameThe person's email, lower case. Widgets count it distinct.
SQL with comments (33 lines)
-- Monthly active users: who logged in, per workspace. Dates from the Month filter.
-- Workspace id to name.
WITH ws AS (
  SELECT CAST(workspace_id AS STRING) AS workspace_id, workspace_name
  FROM system.access.workspaces_latest
),
-- The workspace classes: a LIKE pattern on the workspace name per class; none set means Not classified.
classes AS (
  -- no classes set: every workspace reads Not classified
  SELECT CAST(NULL AS STRING) AS workspace_class, CAST(NULL AS STRING) AS name_pattern, 0 AS priority
  WHERE FALSE
),
-- Each workspace's class: the first pattern its name matches, else Not classified.
ws_class AS (
  SELECT w.workspace_id, w.workspace_name,
         COALESCE(MIN_BY(c.workspace_class, c.priority), 'Not classified') AS workspace_class
  FROM ws w LEFT JOIN classes c ON lower(w.workspace_name) LIKE c.name_pattern
  GROUP BY w.workspace_id, w.workspace_name
),
-- Successful logins (accounts service, login actions, status 200) in the picked month, per workspace and person; account-console logins left out.
logins AS (
  SELECT DISTINCT CAST(workspace_id AS STRING) AS workspace_id,
         lower(COALESCE(user_identity.email, user_identity.subject_name)) AS user_name
  FROM system.access.audit
  WHERE service_name = 'accounts' AND action_name RLIKE '(?i)login'
    AND response.status_code = 200
    AND event_date >= CAST(date_trunc('MONTH', :month) AS DATE)
    AND event_date < add_months(CAST(date_trunc('MONTH', :month) AS DATE), 1)
    AND workspace_id IS NOT NULL AND workspace_id <> 0
)
-- Final SELECT: the rows the widgets read.
SELECT COALESCE(ws.workspace_name, CAST(l.workspace_id AS STRING), 'Account-level') AS workspace, COALESCE(c.workspace_class, 'Not classified') AS workspace_class,
       l.user_name
FROM logins l
LEFT JOIN ws ON ws.workspace_id = l.workspace_id
LEFT JOIN ws_class c ON c.workspace_id = l.workspace_id
-- people only: a service principal logs in under its application id, not an email
WHERE l.user_name LIKE '%@%'

Workspace activity: last audit event, inactive after 90 days

Shows: Every workspace with the day of its last audit event; inactive with none for 90+ days or none in the last 365. Used by: The inactive-workspace tiles and table on Workspace usage.

Why it is built this way: A workspace with no audit event at all for 90 days has no users and no jobs: a candidate to retire. Starting from the list of all workspaces makes ones with no events show up too.

How its tables join

-- Workspace activity: last audit event, inactive after 90 days. Today's view; no dates.
-- Workspace id to name.
WITH ws AS (
  SELECT CAST(workspace_id AS STRING) AS workspace_id, workspace_name
  FROM system.access.workspaces_latest
),
-- The workspace classes: a LIKE pattern on the workspace name per class; none set means Not classified.
classes AS (
  -- no classes set: every workspace reads Not classified
  SELECT CAST(NULL AS STRING) AS workspace_class, CAST(NULL AS STRING) AS name_pattern, 0 AS priority
  WHERE FALSE
),
-- Each workspace's class: the first pattern its name matches, else Not classified.
ws_class AS (
  SELECT w.workspace_id, w.workspace_name,
         COALESCE(MIN_BY(c.workspace_class, c.priority), 'Not classified') AS workspace_class
  FROM ws w LEFT JOIN classes c ON lower(w.workspace_name) LIKE c.name_pattern
  GROUP BY w.workspace_id, w.workspace_name
),
-- Each workspace's last day with any audit event, over the last 365 days.
seen AS (
  SELECT CAST(workspace_id AS STRING) AS workspace_id, MAX(event_date) AS last_activity
  FROM system.access.audit
  WHERE event_date >= date_sub(current_date(), 365)
  GROUP BY 1
),
-- Every workspace, with its last activity and the days since (none when it has no events).
w AS (
  SELECT c.workspace_id, c.workspace_name, c.workspace_class, s.last_activity,
         datediff(current_date(), s.last_activity) AS days_since
  FROM ws_class c LEFT JOIN seen s ON s.workspace_id = c.workspace_id
)
-- Final SELECT: the rows the widgets read.
SELECT COALESCE(workspace_name, workspace_id) AS workspace, workspace_id, workspace_class, 1 AS workspaces,
       COALESCE(CAST(last_activity AS STRING), 'none in 365 days') AS last_activity,
       days_since,
       CASE WHEN last_activity IS NULL OR days_since >= 90 THEN 1 ELSE 0 END AS inactive,
       CASE WHEN last_activity IS NULL THEN 1 ELSE 0 END AS no_events
FROM w
ORDER BY no_events DESC, days_since DESC
