Workspace usage, in brief

A two-minute read. Every query, step and column: the detailed guide.

What it is for

Shows how many people log in per workspace class and per workspace in a month, and which workspaces have had no activity for 90 days or more, as candidates to retire.

How the tables join

Grey: system tables. Blue border: a shared check (its steps are listed under Steps). White: steps of the query. Green: the rows the dashboard shows. ◆ marks the columns the joins use.

  1. access.audit → logins: logins, status 200, emails
  2. access.audit → seen: MAX(event_date)
  3. logins → active users: COUNT(DISTINCT user)
  4. access.workspaces_latest → active users: JOIN ON workspace_id
  5. seen → inactive workspaces: 90+ days or none
  6. access.workspaces_latest → inactive workspaces: LEFT JOIN: all workspaces

The system tables

System tableWhat it holds
system.access.auditOne row per action in the account: who, when, which workspace, the service and action, the request and its response. Kept for 365 days.
system.access.workspaces_latestEach workspace's id and name.

How it works

  • Every login and every action in a workspace writes a row to system.access.audit.
  • Active users counts each person (an email) with a successful login in the month, once; service principals are left out.
  • A workspace with no audit row at all for 90 days, people or jobs, is inactive.

Example: a login becomes an audit row

The query, simplified

The core of it; runs as is in a SQL editor. The dashboard's full queries, step by step: the detailed guide.

-- Active users this month, per workspace: people with a successful login.
SELECT ws.workspace_name, COUNT(DISTINCT lower(a.user_identity.email)) AS active_users
FROM system.access.audit a
JOIN system.access.workspaces_latest ws ON ws.workspace_id = a.workspace_id
WHERE a.service_name = 'accounts' AND a.action_name RLIKE '(?i)login'
  AND a.response.status_code = 200
  AND a.user_identity.email LIKE '%@%'                 -- people, not service principals
  AND a.event_date >= date_trunc('MONTH', current_date())
GROUP BY ws.workspace_name;

-- Inactive: every workspace whose last audit event is 90+ days ago, or that has none.
SELECT ws.workspace_name, MAX(a.event_date) AS last_activity
FROM system.access.workspaces_latest ws
LEFT JOIN system.access.audit a
  ON a.workspace_id = ws.workspace_id AND a.event_date >= current_date() - 365
GROUP BY ws.workspace_name
HAVING MAX(a.event_date) IS NULL OR MAX(a.event_date) < current_date() - 90;

The rules

TermMeans
Active userA person (an email) with at least one successful login (accounts service, a login action, status 200) in the picked month.
ClassThe first LIKE pattern the lower-case workspace name matches; else Not classified.
InactiveNo audit event for 90+ days, or none in the last 365 days.

Good to know

  • Some system tables only hold workspaces in the same cloud region as the metastore; if a workspace is missing, check its region.
  • The audit log keeps 365 days, so last activity can't be older than that.
  • Account-console logins (workspace 0) are left out: they are not a workspace.
