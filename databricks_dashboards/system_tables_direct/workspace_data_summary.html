Workspace data and usage, in brief

A two-minute read. Every query, step and column: the detailed guide.

What it is for

Shows each workspace: what the catalogs it is home to hold, who uses it, which tables and volumes are used, and who has not been seen for a long time. The app's Workspaces tab as a dashboard.

How the tables join

  1. access.table_lineage → home: most reads and writes
  2. home → held: ON catalog
  3. information_schema → held: COUNT per catalog
  4. table_sizes / volume_sizes (job) → held: SUM bytes, files
  5. access.audit → who: events
  6. query.history → who: queries
  7. held → workspaces, tables, volumes, people: LEFT JOIN ON workspace_id
  8. who → workspaces, tables, volumes, people: LEFT JOIN ON workspace_id
  9. access.table_lineage → workspaces, tables, volumes, people: reads, writes per table

          How it works

          • Lineage gives each catalog its home workspace: the one that reads and writes it most.
          • information_schema counts tables, views, columns and volumes per catalog; the sizes job adds bytes and files.
          • Audit and query history give the people per workspace; lineage gives each table's reads and writes.

          Example: one workspace, from lineage to the dashboard

          The query, simplified

          The core of it; runs as is in a SQL editor. The dashboard's full queries, step by step: the detailed guide.

          -- Tables of its home catalogs and active people per workspace, simplified.
WITH home AS (
  SELECT target_table_catalog AS catalog, max_by(CAST(workspace_id AS STRING), n) AS workspace_id
  FROM (SELECT target_table_catalog, workspace_id, COUNT(*) AS n FROM system.access.table_lineage
        WHERE event_date >= current_date() - 90 GROUP BY 1, 2)
  GROUP BY 1
)
SELECT h.workspace_id,
       COUNT(DISTINCT t.table_name) AS tables,
       COUNT(DISTINCT q.executed_by) AS active_people
FROM home h
LEFT JOIN system.information_schema.tables t ON t.table_catalog = h.catalog AND t.table_type <> 'VIEW'
LEFT JOIN system.query.history q
  ON CAST(q.workspace_id AS STRING) = h.workspace_id AND q.start_time >= current_date() - 30
GROUP BY h.workspace_id;

          The pages

          PageWhat it shows
          Table usageOne row per workspace: what the catalogs it is home to hold, who uses it, and a complexity and a usage index. Sizes come from the daily job.
          Volume usageVolumes by home workspace: files and size (daily job), and who read or wrote files in them in the window.
          User activityWho works in each workspace, and who stopped coming: not seen for 90+ days within the last year.

          The rules

          TermMeans
          Home workspaceThe workspace with the most lineage reads and writes of a catalog over 90 days.
          ActiveA person or service principal with an audit event or a query in the workspace in the window.
          InactiveNot seen in the workspace for 90+ days within the last year.
          Not usedA table or volume with no read or write in the window.
          Complexity indexTables, views, columns, table bytes and volume files, each 0-1 on a log scale against the largest workspace, weighted 25/15/20/25/15, times 100.
          Usage indexActive people, service principals and queries the same way, weighted 40/20/40.

          Good to know

          • Sizes and volume files come from the sizes job (DESCRIBE DETAIL, a file listing); tables it can't read show no size, with the error in table_sizes.detail.
          • A catalog with no lineage in 90 days has no home workspace: its tables show under No home workspace and count for no workspace.
          • Volume reads and writes depend on the audit log's request_params path; check the keys below.
