Jobs health, in brief

A two-minute read. Every query, step and column: the detailed guide.

What it is for

Shows which jobs fail, fail now and then (flaky), run slower than usual or wait long for their cluster; which have no timeout or run as a person; which use the wrong size of compute; and what each pipeline costs. Each page answers one of those questions.

How it works

  • Every job run leaves rows in the system tables: its result per attempt (job_run_timeline), each task's setup and run time (job_task_run_timeline), machine use per minute (node_timeline) and its DBUs (billing.usage).
  • The dashboard keeps one row per run and judges its last attempt, so a repaired run that succeeded is not a failure, but the failed attempt's cost still counts.
  • Each job is compared with itself: slow means slow for that job, not slower than other jobs.

The query, simplified

The core of it; runs as is in a SQL editor. The dashboard's full queries, step by step: the detailed guide.

-- One row per run, judged on its last attempt; then per job: runs, failed runs, slow runs.
WITH runs AS (
  SELECT job_id, run_id,
         MAX_BY(result_state, period_end_time) AS result_state,   -- the last row carries the result
         timestampdiff(MINUTE, MIN(period_start_time), MAX(period_end_time)) AS minutes
  FROM system.lakeflow.job_run_timeline
  WHERE period_start_time >= current_date() - 30
  GROUP BY job_id, run_id
),
usual AS (  -- the job's usual time: the median of its successful runs
  SELECT job_id, percentile(minutes, 0.5) AS usual_minutes
  FROM runs WHERE result_state = 'SUCCEEDED'
  GROUP BY job_id HAVING COUNT(*) >= 5
)
SELECT r.job_id,
       COUNT(*) AS runs,
       SUM(CASE WHEN result_state IN ('FAILED', 'ERROR', 'TIMED_OUT') THEN 1 ELSE 0 END) AS failed_runs,
       SUM(CASE WHEN result_state = 'SUCCEEDED' AND minutes > 1.5 * usual_minutes
                 AND minutes - usual_minutes >= 5 THEN 1 ELSE 0 END) AS slow_runs
FROM runs r LEFT JOIN usual u ON u.job_id = r.job_id
GROUP BY r.job_id
ORDER BY failed_runs DESC;

The rules

TermMeans
Failed runIts last attempt ended FAILED, ERROR or TIMED_OUT.
Flaky5+ runs and 20%+ of them failed, but not all.
Always fails3+ runs and every one failed.
Slow runSucceeded, over 1.5x the usual time and 5+ minutes longer.
Slower than usualMedian of the last days (up to 7, at most half the window) vs the rest: 1.5x is Warn, 2x Critical; needs 3+ runs on each side.
Slow cold startp95 cluster start 60 s+ is Warn, 300 s+ Critical.
No timeoutTimeout empty or 0. Warn; Critical when the job spent $200+ in the window.
Ownership riskRuns as a person and is scheduled: Critical. Runs as a person, or creator or run-as missing: Warn.
OversizedWorker CPU p90 under 30%, memory peak under 40%, no swap, over 3+ measured runs. Saving: half the $ when under half those limits, else a quarter; $25+ Warn, $200+ Critical.

Good to know

  • System tables are not real time: job and billing rows can arrive hours late, so today and yesterday read low.
  • Some system tables only hold workspaces in the same cloud region as the metastore; if a workspace is missing, check its region.
  • Only runs that started in the Time Window count; a run that started before it is cut at its start.
